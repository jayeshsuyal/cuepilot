# CuePilot bug sweep — September 11, 2026

Scope: operator desk, projector, API and storage, authenticated bridge, sponsor
adapter boundaries, and current local sponsor connectivity. Destructive browser
checks use a separate SQLite database and loopback ports. The real demo history
and learned Rote procedure are retained.

## Reproduced findings and fixes

| Finding | Reproduction and impact | Fix |
| --- | --- | --- |
| Early live approval races preparation | A fresh Ravi run accepted approval and started execution 6.31 seconds before RocketRide preparation finished. The strict preparation check then rejected the changed phase and blocked the run with zero receipts. | Approval and execution require completed, verified preparation. The desk shows finalization and disables approval until final preparation evidence arrives. |
| Rejected Practice creation leaves a phantom run | Missing presentation or an unready speaker returned HTTP 409 after a queued run had already been committed. It then blocked the next creation in the desk. | Practice creation and planning use one transaction; rejection leaves history and stage unchanged. |
| Unreadable browser storage blanks the desk | Invalid pending-cue JSON or denied sessionStorage access threw during initial rendering, leaving an empty page. | The desk stays readable, retains the saved record and stage/history access, and pauses operator writes with a visible explanation. Execution is not sent if its marker cannot be saved. |
| Bridge accepts duplicate receipt identifiers | Distinct steps/scenes with the same receipt identifier passed the bridge projection. Later API and RocketRide checks rejected them, so no end-to-end false completion was observed. | The bridge independently requires unique receipt identifiers. |
| Old completed runs show recovery warnings | Viewing completed history after configuration edits showed a stale-plan warning and recovery button. | Replacement warnings now apply only to unfinished runs. |

The failed live run is retained as evidence:
`aefea52f-8cca-4032-a5a8-a763079e9814`. Its preparation blocker was
`EXPECTED_PHASE_STATUS_NOT_REACHED`; execution then reported
`RUN_BLOCKED_BY_BACKEND`. Neither accepted a cue. The fix preserves strict
canonical phase verification rather than treating the failure as successful.
